# Защита соединения клиент ↔ VPS

Этот режим предназначен для запуска прокси на VPS. Он использует Fake TLS
с `ee`-секретом, DRS и разделение отправки ServerHello. Для Linux отдельно
предусмотрены TCPMSS и интеграция с установленным `nfqws` из zapret.
Идеи DRS, TCPMSS и серверной десинхронизации сопоставлены с
[mtproto.zig](https://github.com/sleep3r/mtproto.zig).

```text
Telegram ── Fake TLS ── VPS с tg-ws-proxy ── WebSocket/CF ── Telegram DC
```

Меры снижают узнаваемость протокола, но не гарантируют обход DPI. IP VPS,
SNI, размеры и время пакетов остаются видимыми. При полной блокировке IP
одной маскировки недостаточно. Эффективность зависит от сети и проверяется
реальным клиентом и захватом пакетов, а не только успешными тестами кода.

## Домен и HTTPS backend

Используйте свой домен, A/AAAA которого указывает на VPS, и действительный
сертификат для этого домена. Чужой SNI при несовпадающем IP может выдать
маскировку. На отдельном локальном порту должен работать настоящий HTTPS
сайт: обычные подключения и активные пробы будут попадать туда.

Например, HTTP-блок nginx для уже выпущенного сертификата:

```nginx
server {
    listen 127.0.0.1:8443 ssl;
    server_name proxy.example.com;
    ssl_certificate /etc/letsencrypt/live/proxy.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/proxy.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    root /var/www/html;
    index index.html;
}
```

Сертификат и файлы сайта нужно подготовить самостоятельно. TLS-настройки
backend должны соответствовать имитации: TLS 1.3 и X25519, а для клиентов
с гибридным key_share — поддержка X25519MLKEM768 в используемом TLS-стеке.
Fake TLS имитирует рукопожатие и не выполняет настоящий обмен ключами TLS
для авторизованного Telegram-клиента; HTTPS backend обслуживает пробы.

Запуск из корня проекта; замените домен и секрет (32 hex-символа):

```bash
python3 proxy/tg_ws_proxy.py \
  --host 0.0.0.0 --port 443 \
  --secret YOUR_32_HEX_SECRET \
  --fake-tls-domain proxy.example.com \
  --fake-tls-mask-host 127.0.0.1 --fake-tls-mask-port 8443
```

Для привязки к 443 непривилегированному процессу нужен доступ к низкому
порту, например `AmbientCapabilities=CAP_NET_BIND_SERVICE` в systemd.
Это отдельная настройка от сервисов firewall ниже.

Подключайтесь через `ee`-ссылку из логов, заменив `server=0.0.0.0`/локальный
адрес на публичный адрес VPS или `proxy.example.com`, если необходимо.
Секрет имеет форму `ee<32 hex секрета><домен в hex>`.
Старые `dd`-подключения при включённом Fake TLS не принимаются.
Изменение домена требует обновить ссылки у клиентов.

Не направляйте masking backend обратно на публичный порт прокси:
`--fake-tls-mask-host 127.0.0.1 --fake-tls-mask-port 8443` предотвращает такой
цикл и сохраняет исходный SNI клиента. Если backend не указан, используется
`--fake-tls-domain:443`; этот вариант подходит для внешнего cover-сайта,
но не для своего домена, указывающего на этот же прокси.

При запуске [за nginx stream](./FakeTlsNginx.md) задайте тот же отдельный
HTTPS backend. `--proxy-protocol` используйте только на закрытом от внешних
клиентов backend-порту с доверенным frontend. TLS завершается в Fake TLS
обработчике; nginx stream должен передавать байты без TLS termination.

## Что включается вместе с Fake TLS

- **DRS:** первые восемь downstream TLS-записей ограничены 1369 байтами,
  затем предел увеличивается до 16384. Состояние отдельное для каждого
  соединения. Данные MTProto не дополняются произвольным padding.
- **Разделение ServerHello:** после общей случайной задержки 8–24 мс
  отправляется первый байт, затем через 5–15 мс остаток. Содержимое трёх
  TLS-записей и их HMAC сохраняется. Это раздельные TCP-записи, а фактическая
  сегментация зависит от ядра, offload и промежуточных узлов.
- **Активные пробы:** неверный secret, неправильный SNI, повторный ClientHello
  и первый байт, не похожий на TLS, пересылаются настоящему backend.
  Прокси не генерирует свой особый HTTP redirect. Для masking установлен
  idle timeout 30 секунд.
- **Anti-replay:** кеш учитывает аутентифицированную часть ClientHello без
  изменяемых временных байтов. Кеш общий в пределах процесса и переживает
  перезапуск listener, но не перезапуск процесса.
- При запуске размер первого зашифрованного ответа измеряется на заданном
  backend с публичным SNI. Это проверка формы первого ответа, а не полная
  проверка сертификата, PQ-совместимости домена или эффективности обхода.

Параметры для настройки и диагностики:

```text
--no-fake-tls-drs
--no-fake-tls-split
--fake-tls-split-delay-ms 5
--fake-tls-split-jitter-ms 10
```

Оба значения задержки допускают 0..1000 мс. Если наблюдаются проблемы
совместимости, отключайте меры по одной и сравнивайте захваты пакетов.
Без `--fake-tls-domain` эти меры к обычному локальному MTProto не применяются.
Настройки VPS доступны через CLI; редактор настроек трея их не изменяет.

## TCPMSS на Linux VPS

Помощник `deploy/linux/dpi.py` использует только стандартную библиотеку Python.
Он создаёт отдельную цепочку `TGWS_DPI_<port>` в таблице mangle, не очищает
чужие правила и исключает loopback. Сначала просмотрите команды:

```bash
python3 deploy/linux/dpi.py apply --port 443 --mss 88 --dry-run
sudo python3 deploy/linux/dpi.py apply --port 443 --mss 88
sudo python3 deploy/linux/dpi.py status --port 443 --mss 88
```

MSS меняется в **SYN-ACK VPS → клиент**, побуждая клиента отправлять ClientHello
небольшими TCP-сегментами. `88` — начальная настройка из mtproto.zig,
а не универсально подходящее значение: она увеличивает число пакетов и сама
может быть отличительным признаком. Подбирайте значение по сети.
`--mss 0` отключает TCPMSS при использовании NFQUEUE.

Для публичного IPv6 добавьте `--ipv6` при apply/status/remove. Ошибка IPv6
не скрывается. Без этого флага устанавливаются только IPv4-правила.
Нужны `iptables`/`ip6tables`, поддержка TCPMSS ядром и права администратора.
После смены порта сначала удалите правила для старого порта.

## nfqws и автозапуск

Установите совместимый `nfqws` из [zapret](https://github.com/bol-van/zapret)
отдельно. Проверьте поддержку параметров из unit-файла в `nfqws --help`.
Внешние бинарные файлы автоматически не скачиваются.

Шаблоны рассчитаны на репозиторий `/opt/tg-ws-proxy`, `nfqws` по пути
`/opt/zapret/nfq/nfqws`, публичный порт 443 и NFQUEUE 200. Исправьте их,
если установка отличается. Номер очереди не должен быть занят другим сервисом.
Согласуйте его в обоих unit-файлах; TTL 6 тоже требует проверки на вашей сети.

```bash
sudo cp deploy/linux/tg-ws-proxy-{dpi,nfqws}.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tg-ws-proxy-dpi.service
sudo python3 deploy/linux/dpi.py status --port 443 --mss 88 --nfqueue
```

Сервис DPI запускает зависимый nfqws и устанавливает TCPMSS + NFQUEUE.
Для IPv6 добавьте `--ipv6` в обе команды сервиса DPI.
Чтобы сохранять только TCPMSS, удалите зависимость `Requires`/соответствующее
`After` для nfqws и флаг `--nfqueue` из `ExecStart`.

В очередь попадают **исходящие данные VPS → клиент** с публичного порта,
без SYN/FIN/RST. `nfqws` использует `fake,split2`, `md5sig`, TTL и
`any-protocol`, поскольку это серверные ответы, а не ClientHello. Это
отдельный системный процесс, Python-прокси не получает CAP_NET_ADMIN.
`--queue-bypass` пропускает трафик при отсутствии обработчика очереди;
статус правил не доказывает, что nfqws работает — проверяйте также
`systemctl status tg-ws-proxy-nfqws.service` и `journalctl`.

Если публичное соединение принимает nginx, указывайте его публичный порт,
а не внутренний порт Python. Для Docker bridge/DNAT схема OUTPUT может не
подходить: эти шаблоны предназначены для host networking/обычной установки
на VPS. Они не меняют исходные пакеты на устройстве клиента; для этого
нужен отдельный клиентский обработчик. NFQUEUE добавляет обработку пакетов
в userspace, поэтому проверьте скорость и загрузку CPU.

Отключение и очистка:

```bash
sudo systemctl disable --now tg-ws-proxy-dpi.service
sudo systemctl stop tg-ws-proxy-nfqws.service
sudo python3 deploy/linux/dpi.py remove --port 443
```

Добавьте `--ipv6`, если применяли IPv6-правила. Помощник проверяет наличие
установленных правил, повторный apply не добавляет дубликаты, remove можно
повторять. При ошибке apply он пытается удалить только собственные правила.
Команды здесь являются инструкцией для VPS; изменение кода не применяет их
к машине разработчика автоматически.
